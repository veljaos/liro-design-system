# Notes of the "auto" helper: P5.78 Automation rules, P5.79 Merging duplicates (Round 11)

## Decisions (for `docs/decisions.md`, "Liro patterns (Phase 5 part 2)")

- **2026-10-16 — RuleBuilder: "When / If / Then" from the application's data (P5.78).** A new
  component (`components/rule-builder.tsx`, pure logic in `rule-builder-logic.ts`), because the
  library had nothing that builds a condition list: FilterBar filters one list and reports values,
  Diagram draws a process of steps, SettingsPage switches one setting. Three blocks, each a group
  named by its heading (h3 by default, `headingLevel`): **When** (one SelectField of the
  application's triggers, grouped), **If** (conditions joined by "All of these" / "Any of these" —
  the join chosen once there are two; a **group** is a sunken box with its own join, one level
  deep), **Then** (the actions in order, each a SelectField of the application's action kinds and
  its parameters' fields). A condition is a field, a test (operator) and a value; the value's
  field follows the field's kind (`text`, `number` → NumberField, `money` → MoneyField with the
  field's currency, `date` → DateField, `choice` → SelectField, searched from 11 options;
  parameters may also be `longText` → TextAreaField); a test with `noValue` ("is empty") takes
  none; the test is unavailable, with "Choose a field first.", until a field is chosen. Values are
  strings (decimal strings, YYYY-MM-DD, an option's value), `null` while not given.
  **Everything is data:** the triggers, the fields of the chosen trigger (the application passes
  them), the tests each field allows, the actions and their parameters. The builder reports the
  edited rule (`onChange`, a `RuleDraft`) and never evaluates or checks it: the application's
  problems come back as `problems` keyed `'trigger'`, `'conditions'`, `'actions'` or
  `ruleProblemKey(id, part)` ("c2.value", "a1.who") and stand under their fields (block problems
  under the block). The rule **in words** is the application's (`summary`): above the blocks on
  surface.sunken under "In words", `role="status"` (announced politely as it changes).
  **Keyboard, no dragging:** every item names itself ("Condition 2", "Group 1", "Group 1,
  condition 2", "Action 1") on its own line with its tools at the end — Move up, Move down (only
  where it can move) and Remove, 28px CompactIconButtons named "Move up: Condition 2". The focus
  follows each edit once the application passes the new rule back: a new item's first field; the
  moved item's button (the other one when it reached an end, `moveFocusTarget`); after a removal
  the item that takes its place, else the one before, else the list's Add button
  (`focusAfterRemove`). Removing a group's last condition removes the group. New ids from the
  draft (`nextRuleId`: "c4", "g2", "a3"). Changing a condition's field keeps its test only where
  the new field allows it and its value only for the same kind (and currency, and an offered
  choice); changing an action's kind empties its parameters. **Read-only** (`readOnly`, or no
  `onChange`) and **disabled** (`disabledReason`, shown above) show the same blocks as text, the
  values through the provider's `format` (`ruleValueText`; "—" when not given). Loading: three
  skeleton blocks. Phones (`layout`, default below 48em): every field on its own line; on a
  desktop a condition's three fields share a row from a 42rem container. Join words between items
  ("and" / "or") are text, not colour.
- **2026-10-16 — ValueComparison chooses the values to keep (P5.79).** Merging two records needs
  the records side by side and a choice per differing field: ValueComparison already is that
  table (and on phones one card per field, each value labelled with its source), so it takes two
  optional props instead of a new component: `chosen` (row id → the index of the source whose
  value is kept) and `onChoose(rowId, index)`. With `onChoose`, each differing row's values are
  **native radio buttons** (one group per row through `name`, so Tab enters the row once and the
  arrows move the choice; a table row cannot be a Radix radio group), drawn as the system's radio
  (20px, brand.solid with a dot, the focus ring), the whole cell the target; the kept value is the
  neutral selection (D17: surface.selected with the 3px border.selected bar, only the radio blue).
  A row still to choose stays on status.warning.bg with "Choose the value to keep" (icon and
  words); a chosen one says "Chosen" (or the application's `note`). The count reads "4 of 5
  chosen" (`chosenCounts`). Rows the application does not mark as differing are not choices ("Same",
  or its note: "Both accounts are kept"). With `chosen` and no `onChoose` the choice is shown, not
  changed (a check before the kept value, "Chosen" for assistive technology) — the merge's
  confirmation and summary. On phones each differing field's values are a `radiogroup` of boxes
  (source above value), one per line. The application decides which record stays, what it
  preselects, whether the choice is complete and what the merge moves.
- **2026-10-16 — Automation rules are a list, a record and a log (P5.78).** Settings → Automation
  of Kvadrat Gradnja d.o.o. (group BS, `screens-BS.tsx`, `data-BS.ts`): **Automation rules**
  (ListPage; views All / On / Off / Last run failed): the rule's name with the rule in words
  under it, what starts it, the last run with its result in words (Done / Failed / Not met), the
  runs in the last 30 days, and the state — a SwitchField named by the rule with "On" / "Off"
  written beside it (a switch's name stays the rule's, never its state); the row menu has Turn
  off / Turn on (also on phones, where the cards show the state as a badge). **A rule**
  (DetailPage, view and edit in one page, P4.9): the state badge, who changed it, key figures
  (runs in the last 30 days, failed, last run), the rule (RuleBuilder read-only, its words above),
  its runs (DataTable); when the last run failed a danger Alert with the application's message
  and next step above the runs; actions Turn off and Edit. Edit mode: the name and the
  RuleBuilder; the bottom bar Cancel, **Test run** (the application's answer on the latest
  records — "Would run" / "Would not run" with its reason, nothing done — as a section), Save
  (the application's problems under their fields and an error toast; or saved). **New rule**
  (RecordFormPage). **Run log** (ListPage; All runs / Failed): time, the rule and the record as
  links, the result, what happened in the application's words. Every rule, figure, word and check
  is data or the example playing the application (`bsSummary`, `bsProblems`).
- **2026-10-16 — Merging duplicates is choose, see, confirm, result (P5.79).** Master data →
  Possible duplicates (group BT, `screens-BT.tsx`, `data-BT.ts`): the pairs the application found
  (both records with their codes, why: "Same PIB 106543218", "Same barcode 8600981000101", when
  found, the state in words — To review, Merged, Not duplicates with who decided). **Merge
  partners / Merge items** (DetailPage): "Which record stays" (CandidateList, one choice, each
  record's reason and figure; the application proposes the older and preselects its values;
  choosing the other record takes the application's other preselection and counts); "Values to
  keep" (ValueComparison with `chosen` / `onChoose`, columns "Beton Mix d.o.o. (stays)" /
  "Beton-Mix doo (merged into it)"); "What will happen" (KeyValueList of the application's counts:
  documents and open items moved, bank accounts kept, the inbox's matching, the merged record
  closed with its code leading to the kept one). Actions: Not duplicates, then **Merge** (caution,
  the main action) unavailable with its reason until every differing field has a value ("Choose
  the value to keep for 1 more field."). Merge opens the **IrreversibleConfirmDialog**: the
  action as title, "Beton-Mix doo into Beton Mix d.o.o." as subject, the consequence, the values
  kept as a preview (ValueComparison `chosen` only), the merged record's code typed. **The
  result** is the kept record's page: a success Alert with who merged what and when, what moved,
  the values kept, the documents that moved here as links (invoice 2026-1187 in the document
  inbox; the cement's receipt and issue at Site Liman 4).

## New components and why

- **RuleBuilder (new).** Nothing in the library builds a list of conditions with joins and groups
  and an ordered list of actions with parameters: FilterBar filters a list (fixed filters, values
  only), Diagram draws a process, BulkEditDrawer edits fields of records. Assembled inside from
  SelectField, NumberField, MoneyField, DateField, TextField, TextAreaField, Button,
  CompactIconButton, FieldMessage and Skeleton. Its logic is pure and tested
  (`rule-builder-logic.ts`, `rule-builder.test.tsx`).
- **ValueComparison `chosen` / `onChoose` (new optional props, no new component).** The merge's
  chooser is the comparison that already shows two records side by side, with the same phone
  cards; a separate component would have repeated it.
- Everything else is assembled: ListPage, DataTable (cards on phones), SwitchField, StatusBadge,
  DetailPage (view / edit, sections, key figures), RecordFormPage, FormSection, SectionCard,
  ActionGroup (UnavailableAction reason), Alert, CandidateList, KeyValueList,
  IrreversibleConfirmDialog (with `preview`), RelatedDocuments, Toaster.
