  **Chosen: TanStack Table, already ours.** No maintained MIT pivot library exists that is
  accessible and themeable; and every pivot library above (MIT or not) computes the aggregates
  itself, while in Liro the application computes (D1, D4: decimal strings, totals arrive
  computed). What TanStack Table gives: the application's column tree as nested column groups,
  whose header groups carry each header cell's column and row span (two or more header rows,
  a shallow total column spanning them — `header.rowSpan`), and the row tree drawn through the
  expanded row model (`rowExpandingFeature`, `createExpandedRowModel`, `getSubRows`) from the
  open groups. Its `columnGroupingFeature` and `rowAggregationFeature` (grouping and aggregating
  in the browser) are **not** used.

- **2026-10-16 — `@veljaos/ui/pivot`, a subpath of its own (P5.77).** As `charts`, `gantt` and
  `map`: a tsup entry `pivot`, `exports["./pivot"]` in `packages/ui/package.json`, a consumer-check
  example (`apps/consumer-check/src/PivotExample.tsx`) rendered from the packed tarball. TanStack
  Table is also used by the main entry (DataTable), so the subpath keeps only the pivot's own code
  (grid, chooser, logic) out of `dist/index.js`.

- **2026-10-16 — Pivot: the application computes, the library lays out (P5.77).** `Pivot` takes
  `fields` (dimensions and measures with the application's aggregations, a dimension's values
  for filtering), `value` (the layout: rows, columns, values with their aggregation, filters with
  their kept values) and `onChange`, and `result` (the application's column tree, row tree and
  grand total; every cell a decimal string by leaf column key, null "—"). It never adds,
  averages or counts. **Subtotals are the group's own row** (compact form: a group row carries
  its figures, semibold, and its members under it), so no separate subtotal rows; total columns
  (`total`) and the grand total row are semibold on `surface.sunken`, the grand total under a
  1px `border.strong` line in a `tfoot`, as DataTable's totals. A column (or a group above it)
  sets how its figures are written (`kind` 'number' | 'money' | 'percent', `currency`, `decimals`)
  through the provider's `format`; tabular, end-aligned. `loading`: skeleton rows the first time,
  then "Updating…" at the toolbar's end with the old figures kept (`aria-busy`), never a
  translucent overlay. States: no value chosen ("Choose a value", with "Choose fields"), `error`
  with Try again (`onRetry`), no figures for the layout. A filter with no value chosen keeps every
  value; a measure stands in Values once (its aggregation changes in place).

- **2026-10-16 — The field chooser: buttons and menus, no dragging (P5.77, WCAG 2.5.7).** Filters,
  Columns, Rows and Values (a spreadsheet field list's order), each an h3 and a list, then
  "Available fields". A used field has a 28px "Options: <field>" menu: Move up, Move down, Move to
  <each other area it may stand in>, Remove; a value has its aggregation as a SelectField (one
  aggregation is plain text), a filter its kept values as a MultiSelectField in summary mode ("All
  values" while none is chosen). An unused field is added by "Add <field> to <area>" when it fits
  one area, else by an "Add <field>" menu of the areas. **No dragging at all**: the owner made
  dragging optional; every change takes one or two presses, and a drag would only duplicate the
  menus. Every change is reported at once (`onChange`); there is no "Apply" — the application
  shows `loading` while it computes. On wider screens the chooser is a 288px start column beside
  the grid, shown and hidden by "Fields" (`aria-expanded`, `aria-controls`; open by default); on
  phones it is a full-screen sheet (the Drawer at the phone's width) with "Done", closed by
  default. Without `onChange` the layout is fixed and there is no chooser.

- **2026-10-16 — The pivot grid: a treegrid around a layout table (P5.77).** A WAI-ARIA treegrid,
  one cell in the tab order: arrows cell by cell (ArrowRight towards the end, so mirrored in right
  to left), Home / End (with Ctrl or Cmd the grid's first / last cell), Page Up / Down by ten rows
  (`pivotKeyTarget`, tested); Enter or Space on a group's row header opens or closes it (the row
  carries `aria-level` and `aria-expanded`), on a figure reports it (`onDrillDown` with the row
  and column keys and their labels from the top, `PivotCellRef`); a press does the same. A figure
  that opens is underlined (dotted) on hover, never link-blue (D17: the grid would be all blue).
  **Markup:** the treegrid is a `div` (the scroll region) around a `<table role="presentation">`
  whose rows and cells carry `row`, `columnheader` (with `aria-colspan` / `aria-rowspan`),
  `rowheader` and `gridcell`: the native `colspan` / `rowspan` draw the multi-row header, and
  jsx-a11y's strict config forbids an interactive role on `<table>` itself (no new lint
  exception). The hint ("Move between the figures with the arrow keys…") describes the grid.
  **Sticky (D21):** the `thead` carries `STICKY_HEAD` and `data-sticky-head` (the header rows move
  as one below the shell, `useStickyHead` on the region), the row headers `STICKY_START` on an
  opaque surface (`surface.raised`, the grand total's `surface.sunken`), the corner both and
  `data-sticky-start`, the region `STICKY_CLEARANCE`. The corner names the column fields
  (tertiary) over the row fields ("Region / Product line"). Groups: the first level open by
  default (`defaultExpanded`, or controlled `expanded` / `onExpandedChange`), "Expand all" /
  "Collapse all" in the toolbar. **Phones:** the same grid, read in place — it scrolls sideways
  inside its card with the first column at the start (min 9rem), the page never does (D19);
  figures still open their records.

- **2026-10-16 — Export and drill-down are reported (P5.77).** `exportAction: { formats,
  onExport }`: one format is an "Export" button (the `export` intent), several a menu of the
  application's formats; shown only when a value is chosen; the application makes the file (as
  a job, a toast). `onDrillDown(cell)`: the application opens the records — the examples use an
  end Drawer titled by what it lists, the figure as its bold `subject` ("Liman 4 · 5120 Material ·
  Sep 2026 · Amount", D22), with a DataTable (cards on phones) of the latest ten and the
  application's count.

## New components and why

- **`Pivot`** (`@veljaos/ui/pivot`): nothing existing lets the user choose the layout of an
  analysis. DataTable shows records with fixed columns (one header row, no row groups); TreeTable
  has row groups but one header row and fixed columns; the StatutoryFormPage grid has groups over
  sub-columns but is a page template for an official form with fixed parts. The pivot's grid
  reuses their rules (DataTable's totals look, the shared sticky mechanism of `sticky-head.ts`,
  the statutory grid's header cells) and the chooser is built from existing components
  (CompactIconButton, DropdownMenu, SelectField, MultiSelectField, Drawer, EmptyState,
  ErrorState, Skeleton, Spinner). No new prop on an existing component.
